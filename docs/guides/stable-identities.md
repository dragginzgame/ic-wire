# Stable Wire identities

Core and Endpoint have separate release groups. The [root manifests](../../Cargo.toml)
and [current handoff](../status/current.md) own the selected supplier cohort;
this guide describes the boundaries rather than duplicating version pins.

## Owners and release groups

| Owner | Responsibility | Release group |
| --- | --- | --- |
| `ic-wire` | Codec, limits, framing, field types and host schemas | Core |
| `ic-wire-derive` | Serde layout metadata derive | Core |
| `ic-wire-endpoint` | Typed handlers, contracts and runtime integration | Endpoint |
| `ic-wire-endpoint-macros` | Query/update expansion | Endpoint |
| Platform Types | Principal/Account identity and Serde representation | Upstream |
| Platform Runtime | Exports, executor and singleton guard | Upstream |
| Private qualification workspace | Benchmarks and integration proofs | Unpublished |

Core implements its existing schema trait for canonical Types through the
optional `platform-types` feature. No wrapper, second trait or Platform-to-Wire
dependency is needed. Endpoint owns its macro implementation; changing that
implementation does not itself require a Core release. Codec-only consumers do
not need Wire metadata or its derive dependency.

## Consumer migration

A compatible patch can be selected through a consumer lockfile without
republishing every dependent library. A pre-1.0 minor change to public Rust type
identity or payload layout requires consumer qualification. Align canonical
Types and Runtime selections, keep one execution guard and use the supported
Core/Endpoint pairing tested by `check-compatible-consumers`.

Wire does not negotiate old layouts or supply fallback readers. Serde field and
variant order determines encoding; method IDs identify routes, not schemas.
Automatic IDs depend on exported names and do not fence a layout change.
Consumers coordinate identities, generated clients, stored unframed values and
original retry/hash bytes when changing a contract.

For the historical Account change, see the [0.16 migration](../../releases/core/0.16.md):
present subaccounts changed from `01 + 32 bytes` to `01 20 + 32 bytes`; absent
subaccounts remain `00`. Do not reapply that migration to an already aligned
consumer or infer a new layout change from a supplier update alone.

## Grouped maintainer flow

[Release policy](../../ci/cargo-release-groups.json) lists only the four public
packages. Each retains a literal version. Private packages live in the independent
`qualification/` workspace with their own lock and preserved versions; they are
not public release-group members.

Group ledgers live at `releases/<group>/CHANGELOG.md`; the root changelog is an
index. Shared preparation updates the selected public metadata and both relevant
locks atomically, preserving private versions and unrelated suppliers. The
Makefile selects the release editor; this guide does not pin another version.

Use the [development release procedure](development.md#snapshot-maintenance-and-release-boundary)
for capture, qualification and recovery. Select `RELEASE_GROUP` explicitly and
supply the ordered `RELEASE_GROUPS` roster when starting a batch. Publish Core
before a dependent Endpoint release. Publication subsets must remain within the
selected group; never upload a version again to repair a partial release.

## Qualification and remaining acceptance

The release roster and [group-validation guide](group-validation.md) own the
required checks. Compatibility qualification covers current/published package
identities, standalone host/Wasm consumers and generated byte conformance.
Runtime supplier changes also require the installed Endpoint tests for admission,
exports, guard composition and rollback.

Use current Rust 1.99.1 checks. Older Rust 1.91 results and supplier-move size
figures in [historical findings](../evidence/stable-identities.md) describe their
original source only. [Delivery receipts](../../releases/receipts/README.md)
record past publication; they do not prove that old build artifacts still exist.
